DO YOU COPY?
Technical Design and Architecture
Status: Initial Technical Specification
Platform: PC
Engine: Godot 4.7
Language: GDScript


1. PURPOSE

This document defines the technical structure for Do You Copy?.

The game is a 25-35 minute first-person radio horror scenario.

Technical priorities:
- fast iteration
- clear ownership
- simple debugging
- few runtime dependencies
- reliable scripted progression
- stable voice playback
- deterministic branching
- automated tests for scenario failures

Do not add architecture for a large game.


2. TECHNOLOGY STACK

ENGINE
Godot 4.7

LANGUAGE
GDScript

RENDERER
Forward+

3D WORKFLOW
Blender -> glTF / GLB -> Godot

Use Godot built-in systems before you add a dependency.


3. THIRD-PARTY ADDONS

Use only addons that replace important infrastructure.

3.1 Dialogue Manager

Use Dialogue Manager for:
- authored radio dialogue
- conditional dialogue
- dialogue mutations
- static line IDs
- manual dialogue progression

Do not use a standard dialogue balloon as the main presentation.

Present dialogue through:
- radio audio
- terminal log
- workstation state

Dialogue Manager owns dialogue content.

Dialogue Manager does not own:
- radio tuning
- scenario state
- channel quarantine
- player interaction
- field state

3.2 Godot State Charts

Use Godot State Charts for the contact lifecycle.

Primary states:

WAITING
-> TUNING
-> RECEIVING
-> VERIFYING
-> DECIDING
-> RESOLVING
-> COMPLETE

Use explicit events for transitions.

Examples:
- contact_started
- signal_acquired
- opening_voice_finished
- repeat_requested
- authentication_requested
- authentication_finished
- decision_made
- resolution_finished

State Charts owns the current interaction state.

State Charts does not own:
- persistent run data
- dialogue content
- radio implementation

3.3 GdUnit4

Use GdUnit4 for scenario tests.

Test:
- contact reachability
- state transitions
- branch resolution
- quarantine behavior
- GHOST knowledge
- ending reachability
- invalid content references
- scenario soft-locks

Do not prioritize automated tests for:
- lighting
- cosmetic animation
- room decoration

6. OWNERSHIP RULE

Use this direction:

PARENT CONFIGURES CHILD.
CHILD REPORTS TO PARENT.

Use signals for child-to-parent communication.

Do not let a reusable child search the scene tree for gameplay objects.

Do not use absolute node paths to reach unrelated systems.


7. PLAYER RIG

PlayerRig owns:
- mouse look
- constrained camera movement
- interaction ray
- current interaction focus
- player arm presentation

PlayerRig does not know:
- active contact
- agent state
- GHOST state
- authentication result
- scenario progression

Do not install a general FPS controller unless the game requires free walking.


8. INTERACTION MODEL

Use small interaction scripts.

Base type:

class_name Interactable
extends Node3D

func can_interact() -> bool:
    return true

func interact() -> void:
    pass

func begin_drag() -> void:
    pass

func drag(delta: Vector2) -> void:
    pass

func end_drag() -> void:
    pass

Examples:
- TuningKnob
- CleanupKnob
- AuthenticationButton
- RepeatButton
- ResponseButton
- QuarantineSwitch
- PaperDocument

Do not create one universal interaction component with many unrelated configuration flags.

PlayerRig detects the object.

The object handles local behavior.

The object emits gameplay events.


9. RADIO CONSOLE

RadioConsole owns:
- current frequency
- target frequency
- tuning tolerance
- signal-quality control
- current signal quality
- local indicators

RadioConsole does not own:
- speaker identity
- dialogue branch
- scenario outcome
- field consequence

Use a simple signal model.

Example:

frequency_error =
    abs(current_frequency - target_frequency)

tuning_quality =
    1.0 - clamp(
        frequency_error / tolerance,
        0.0,
        1.0
    )

signal_quality =
    tuning_quality * cleanup_quality

Suggested presentation:

0.00-0.20
Mostly static.

0.20-0.45
Partial speech.

0.45-0.70
Understandable speech with noise.

0.70-1.00
Clear speech.

A practiced player should acquire a normal signal in 5-10 seconds.

Do not implement a full software-defined radio simulation.


10. PROGRAMMED DISPLAYS

Use 2D Control scenes inside SubViewport nodes.

Assign each ViewportTexture to the correct 3D monitor material.

Do not build complex screen UI directly in 3D.


11. SPECTRUM MONITOR

SpectrumMonitor owns presentation only.

Show:
- active carriers
- tuned frequency
- signal strength
- abnormal carriers when required

Use:
- custom _draw()
- deterministic generated spectrum

Optional:
Use AudioEffectSpectrumAnalyzer for live voice visualization.

Do not require the player to understand a physically accurate FFT.


12. TERMINAL MONITOR

TerminalMonitor shows only gameplay information.

Show:
- active frequency
- claimed callsign
- last verified location
- current objective
- recent communication log
- known agent status

Do not build:
- a full fake operating system
- unrelated applications
- arbitrary command-line features

The terminal is an evidence source.

The terminal can become unreliable later.


13. FIELD MAP

Use 3-4 locations.

Show:
- last verified position of ECHO-ACTUAL
- last verified position of ECHO-2
- simple route connections

REROUTE uses authored destinations.

Do not make the map a strategy system.


14. CONTACT DEFINITION

Use a custom Resource.

Example:

class_name ContactDefinition
extends Resource

@export var id: StringName

@export_group("Signal")
@export var frequency: float
@export var tolerance: float = 0.08
@export var noise_level: float = 0.3
@export var channel: StringName

@export_group("Identity")
@export var claimed_callsign: StringName
@export var actual_source: StringName

@export_group("Dialogue")
@export var dialogue: DialogueResource
@export var opening_cue: StringName

@export_group("Scenario")
@export var required_flags: Array[StringName]
@export var excluded_flags: Array[StringName]

Store contacts in:

content/contacts/
├── contact_01_training.tres
├── contact_02_echo2.tres
├── contact_03_first_fake.tres
├── contact_04_route.tres
├── contact_05_duplicate.tres
├── contact_06_old_auth.tres
├── contact_07_learned_copy.tres
└── contact_08_final.tres

ContactDefinition owns:
- signal setup
- claimed identity
- dialogue entry point
- availability conditions

ContactDefinition does not execute scenario logic.


15. SCENARIO STATE

ScenarioState is a scene-local Node.

ScenarioDirector owns ScenarioState.

Suggested data:

class_name ScenarioState
extends Node

var echo_actual_location: StringName
var echo_2_location: StringName

var echo_actual_reachable := true
var echo_2_reachable := true

var quarantined_channels: Dictionary[StringName, bool] = {}

var ghost_access := 0
var ghost_knowledge: Dictionary[StringName, bool] = {}

var flags: Dictionary[StringName, bool] = {}

ScenarioState owns persistent run data.

ScenarioState does not:
- play audio
- change UI
- manipulate workstation nodes
- advance dialogue

Dialogue Manager can read ScenarioState as extra game state.


16. SCENARIO DIRECTOR

ScenarioDirector owns:
- contact order
- contact selection
- contact eligibility
- radio configuration
- gameplay consequences
- ending evaluation
- connection between scenario events and State Charts

ScenarioDirector does not:
- render UI
- read raw player input
- move radio controls
- play voice files directly

Typical flow:

load ContactDefinition
-> configure RadioConsole
-> enter TUNING
-> wait for signal_acquired
-> start opening dialogue
-> enter RECEIVING
-> wait for voice completion
-> enter VERIFYING
-> process REPEAT or AUTHENTICATE
-> enter DECIDING
-> receive player response
-> apply state changes
-> enter RESOLVING
-> play consequence
-> select next contact


17. DIALOGUE RUNNER

DialogueRunner connects Dialogue Manager to game presentation.

DialogueRunner owns:
- request next dialogue line
- read static line ID
- play the matching voice asset
- append transcript text
- report line completion
- report sequence completion

DialogueRunner does not choose scenario branches independently.

Use stable line IDs.

Examples:
- C05_FAKE_01
- C05_FAKE_02
- C05_REAL_01
- C07_AUTH_RESPONSE

Voice files:

content/voices/generated/
├── C05_FAKE_01.ogg
├── C05_FAKE_02.ogg
├── C05_REAL_01.ogg
└── C07_AUTH_RESPONSE.ogg


18. TTS PIPELINE

Do not use runtime TTS in the initial version.

Generate authored voice files before the build.

Pipeline:

dialogue source
-> local TTS tool
-> WAV or OGG
-> Godot import
-> radio audio processing

Use Piper or another lightweight offline TTS tool during development.

Tool:

tools/generate_voices.py

Use one stable voice profile for each agent:
- ECHO-ACTUAL
- ECHO-2

When the GHOST copies an agent, use the same voice profile.

Do not create a separate monster voice.

Use text, context, and speech behavior as the main identity clues.


19. AUDIO ARCHITECTURE

Use Godot audio buses.

Suggested layout:

Master
├── Environment
├── Interface
└── Radio
    ├── Voice
    └── Static

Suggested Radio/Voice effects:

BandPass
-> Compressor
-> light Distortion
-> HardLimiter
-> SpectrumAnalyzer

RadioVoice owns voice playback.

RadioStatic owns radio noise.

RadioConsole provides signal quality.

Use signal quality to control:
- voice level
- noise level
- filter values
- limited dropout

Do not hide required information with audio effects.

REPEAT must remain available when required information is not clear.


20. PLAYER ARM

Use one rigged arm.

Animate only repeated actions:
- turn frequency dial
- adjust signal-quality control
- use authentication control
- use push-to-talk
- use quarantine control

Paper handling is optional.

Do not create unique animations for visual-only props.

Gameplay state should change from interaction events.

Do not depend on animation completion unless timing is required.


21. QUARANTINE SYSTEM

QUARANTINE CHANNEL is the only irreversible sacrifice system.

Flow:

QuarantineControl emits:
quarantine_requested(channel)

ScenarioDirector checks:
- channel is active
- channel can be quarantined
- current contact state permits quarantine

ScenarioState records:
quarantined_channels[channel] = true

RadioConsole blocks normal future acquisition on that channel.

ScenarioDirector selects the correct later content.

The system must be deterministic.


22. ENDINGS

Use three ending families.

CONTAINED
The operator keeps enough genuine communication and isolates the GHOST.

ISOLATED
The operator stops the GHOST but loses one or both agents.

OPEN_LINE
The operator leaves a critical route open or trusts the copied identity at a critical point.

ScenarioDirector selects the ending from ScenarioState.

Do not distribute ending-selection logic across dialogue files.


23. AUTOLOAD POLICY

Do not create gameplay autoloads unless a real global lifetime is required.

Do not create:
- GameManager
- AudioManager
- RadioManager
- ScenarioManager
- InteractionManager

Prefer scene-local ownership.

Third-party addons can use their required autoloads.

A Settings autoload is acceptable if persistent settings are added.


24. SIGNAL CONTRACTS

Recommended signals:

RadioConsole:
- signal_acquired(frequency: float)
- tuning_changed(frequency: float)
- quality_changed(value: float)

AuthenticationControl:
- authentication_requested

RepeatControl:
- repeat_requested

OperatorDecisionPanel:

QuarantineControl:
- quarantine_requested(channel: StringName)

DialogueRunner:
- sequence_started
- line_started(line_id: StringName)
- line_finished(line_id: StringName)
- sequence_finished

ScenarioDirector subscribes to gameplay events.

Do not use a global event bus.


25. TEST STRATEGY

Primary test target:
scenario correctness.

Create a scenario test harness that does not require 3D interaction.

The harness must support:
- load ScenarioState
- load ContactDefinition
- inject decisions
- advance contacts
- inspect final state

Required tests:

CONTACT DATA
- contact IDs are unique
- dialogue resources exist
- opening cues exist
- channels are valid
- callsigns are valid
- required flags are valid

FLOW
- training reaches contact 2
- each contact can resolve
- no contact can remain blocked permanently
- final contact is reachable

QUARANTINE
- quarantined channels remain blocked
- alternate content resolves
- required endings remain reachable

GHOST
- GHOST knowledge changes in the correct order
- copied authentication is not available before the GHOST learns it
- invalid state combinations are rejected

ENDINGS
- CONTAINED is reachable
- ISOLATED is reachable
- OPEN_LINE is reachable


26. PERFORMANCE

Performance priorities:
- stable frame time
- no audio stutter
- fast startup
- low-cost monitor rendering

Potential high-cost systems:
- high-resolution SubViewports
- frequent spectrum updates
- unnecessary dynamic lights
- high shadow resolution

Use only the display resolution required by the physical monitor size.

Update a display only as often as its content requires.

Do not optimize static room geometry before profiling.


27. SAVE AND RESTART

Do not build a full save system for the initial version.

Required:
- restart run
- return to title

Optional:
- one development checkpoint before the final section

Store persistent settings separately if required.


28. VERSION CONTROL

Commit:
- Godot project files
- source assets
- dialogue source
- generated voice files required by the build
- voice generation tools

Do not commit:
- .godot/ cache
- generated import cache
- temporary Blender files
- local editor state

Keep generated voice assets reproducible from source dialogue when possible.

30. ARCHITECTURE RULES

- Organize the project by feature.
- Prefer composition to deep inheritance.
- Use signals for child-to-parent communication.
- Let parents configure children.
- Keep persistent gameplay state in ScenarioState.
- Keep ScenarioState scene-local.
- Do not create gameplay autoload managers.
- Let Dialogue Manager own dialogue content.
- Let State Charts own the contact lifecycle.
- Let ContactDefinition own contact configuration.
- Let ScenarioDirector own scenario progression.
- Let workstation components own local interaction behavior.
- Let UI present state only.
- Keep audio evidence understandable.
- Keep scenario behavior deterministic when possible.
- Test the complete scenario without 3D interaction.
- Remove an abstraction if it does not simplify this game.
