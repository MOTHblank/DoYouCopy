DO YOU COPY?
Game Design Document
Status: Core Design
Platform: PC
Target play time: 25-35 minutes
Genre: First-person radio operations horror / identity verification


1. PURPOSE

Do You Copy? is a short first-person horror game.

The player operates a communications station for two field agents.

Each major contact uses the same question:

IS THE SPEAKER THE PERSON THEY CLAIM TO BE?

The player tunes to a signal, verifies the speaker, and sends an operational response.

A hostile entity is present in the communications network. This document calls the entity the GHOST.

The GHOST learns:
- agent voices
- callsigns
- procedures
- authentication answers
- recent operational information

The game must provide a complete scenario in approximately 30 minutes.


2. CORE GAME LOOP

The core loop is:

TUNE -> VERIFY -> DECIDE -> CONSEQUENCE

2.1 TUNE

The player finds and cleans the active signal.

The player uses:
- one frequency control
- one signal-quality control

A practiced player should acquire a normal signal in 5-10 seconds.

Tuning supports the operator role. Tuning is not the main puzzle.

2.2 VERIFY

The player compares the speaker with available evidence.

Evidence can include:
- voice
- callsign
- assigned frequency
- last verified location
- current task
- authentication response
- recent contacts
- speech habits
- contradictions with another agent

The game must not display a REAL / FAKE result.

2.3 DECIDE

The player sends one operational response.

Available responses:
- HOLD
- PROCEED
- REROUTE
- QUARANTINE CHANNEL

Do not use a generic TRUST / FAKE button.

2.4 CONSEQUENCE

The decision changes later contacts.

Typical consequences:
- an agent changes location
- an agent becomes unreachable
- a route becomes unavailable
- an agent changes their trust in the operator
- the GHOST gains information
- a channel becomes unavailable

Most wrong decisions should continue the scenario.


3. DESIGN PRINCIPLES

3.1 Identity is the main puzzle

Do not add generic puzzle types.

Do not use:
- arbitrary number sequences
- unrelated ciphers
- memory minigames
- logic puzzles that do not affect identity verification

Use puzzles only when they support verification or field decisions.

3.2 Establish a rule before the GHOST breaks it

The player must first learn normal procedures.

The GHOST then makes those procedures less reliable.

Escalation order:
1. noisy or incorrect information
2. impossible information
3. copied voice and identity
4. copied authentication
5. unreliable station data

3.3 Use a small field model

Track only data that can affect a later contact.

Do not add a strategy layer.

3.4 Reuse the same room and equipment

Create new content with:
- voice lines
- screen data
- paper data
- audio
- lighting
- state changes

Do not add new environments for the 30-minute version.


4. PLAYER ROLE

The player is the communications operator for field team ECHO.

The field team has two agents.

ECHO-ACTUAL
- team lead
- follows radio procedure
- uses concise speech
- expects read-back
- usually says "Operator" before a direct request

ECHO-2
- second field agent
- uses informal speech
- abbreviates some location names
- sometimes speaks before a formal identification
- is easier to identify by speech habits

The player does not enter the field area.

The player can:
- tune a frequency
- clean a signal
- inspect records
- request REPEAT
- request AUTHENTICATION
- send HOLD
- send PROCEED
- send REROUTE
- quarantine a channel


5. WORKSTATION

The game uses one compact communications room.

Only the following objects need full gameplay interaction.

5.1 RADIO RECEIVER

Functions:
- set frequency
- set signal quality
- show channel state

Use the radio in every major contact.

5.2 SPECTRUM DISPLAY

Render the display in code.

Functions:
- show active carriers
- show tuned frequency
- show signal strength
- later show abnormal carriers

The display must be readable without detailed radio knowledge.

5.3 TERMINAL

Render the terminal in code.

Show only:
- active frequency
- claimed callsign
- last verified location
- current objective
- recent communication log
- known agent status

Do not build a full fake operating system.

The terminal is one evidence source. It is not always correct.

5.4 PAPER REFERENCE

Use physical paper for:
- authentication challenges
- frequency assignments

The paper gives the player an information source that is separate from the terminal.

5.5 FIELD MAP

Use 3-4 named field locations.

Show:
- last verified position of ECHO-ACTUAL
- last verified position of ECHO-2
- simple route connections

The map is reference material.

Do not make the map a strategy minigame.

5.6 MICROPHONE / PUSH-TO-TALK

Use this object to send the selected response.

The player arm should move to this object for important decisions.

5.7 QUARANTINE CONTROL

Use one protected switch or button.

The control permanently blocks the selected channel.

Introduce this control after the player understands normal communication.

5.8 NON-CORE PROPS

The following objects can be visual only:
- printer
- patch panel
- door
- shelves
- filing cabinets
- lights
- general clutter

Do not add gameplay to a prop unless the scenario needs it.


6. IDENTITY VERIFICATION

Each agent has four evidence groups.

STATIC DATA
- callsign
- primary frequency
- role

CURRENT DATA
- last verified location
- current task
- latest route change

AUTHENTICATION DATA
- active challenge
- expected response

BEHAVIOR DATA
- speech habits
- radio procedure habits

The GHOST gains access to these evidence groups during the scenario.

Authentication confirms knowledge. Authentication does not confirm identity.


7. AUTHENTICATION

Use challenge-response authentication.

A challenge must take only a few seconds.

Example:

CHALLENGE DELTA-4
"What has keys but opens no locks?"

EXPECTED RESPONSE:
KEYBOARD

The player selects AUTHENTICATE.

The agent gives a response.

The player compares the response with the paper reference.

Use 4-6 challenge-response pairs in the complete scenario.

Escalation:

EARLY
- genuine agents give correct responses
- false or noisy contacts fail

MIDDLE
- a suspicious speaker gives an old valid response

LATE
- the GHOST gives the current correct response because it heard the challenge earlier

FINAL
- the player must use context and contradictions because authentication is not sufficient


8. CHANNEL QUARANTINE

QUARANTINE CHANNEL is the only sacrifice mechanic.

When the player quarantines a channel:
- the station blocks the channel for the rest of the run
- normal future contacts on that channel are lost
- the GHOST cannot use that route normally
- a genuine agent can lose their main communication route

The action cannot be reversed.

Use no more than two important quarantine decisions in the 30-minute scenario.

Do not add other sacrifice systems to the initial version.


9. THE GHOST

Do not give the GHOST an obvious monster voice.

When the GHOST copies an agent, use the same voice identity and normal radio processing as that agent.

Escalation:

STAGE 1 - SIGNAL ERROR
- crosstalk
- drift
- incomplete identifier
- plausible equipment fault

STAGE 2 - CONTRADICTION
- wrong location with the correct voice
- information that the agent should not know
- impossible timing

STAGE 3 - COPY
- correct voice
- correct callsign
- believable report
- one contextual error

STAGE 4 - LEARNING
- correct current authentication
- copied speech habit
- information learned from earlier contacts

STAGE 5 - MACHINE ERROR
- terminal data changes
- a quarantined channel shows a carrier
- paper data and terminal data disagree
- a contact appears to originate from the operator station

Escalate through unreliable information.

Do not depend on repeated visual jumpscares.


10. 30-MINUTE SCENARIO

Use approximately eight major contacts.

Each contact must have one clear design purpose.

00:00-03:00 - TRAINING

Speaker:
ECHO-ACTUAL

Teach:
- TUNE
- signal cleaning
- terminal reading
- AUTHENTICATE
- PROCEED

No horror event is required.

Purpose:
Teach the complete core loop.

03:00-06:00 - NORMAL ECHO-2 CONTACT

Speaker:
ECHO-2

Teach:
- map use
- HOLD / PROCEED
- ECHO-2 speech habits

Purpose:
Teach behavior as identity evidence.

06:00-09:00 - FIRST DISCREPANCY

A weak contact claims to be ECHO-2.

Use one clear error:
- wrong frequency
- wrong location
- wrong authentication response

Purpose:
Teach the player to verify identity.

The correct response must be discoverable from available evidence.

09:00-13:00 - FIELD CONSEQUENCE

The agents report the result of the previous decision.

The player selects a route for one agent.

Use two plausible route options.

Purpose:
Show that decisions change later contacts.

13:00-17:00 - DUPLICATE VOICE

Two contacts claim to be ECHO-ACTUAL.

Both use the correct voice.

One contact contradicts recent operational information.

Purpose:
Reveal the main horror mechanic.

17:00-21:00 - OLD AUTHENTICATION

A suspicious speaker gives an answer that was valid earlier.

Purpose:
Show that authentication can be copied.

After this contact, enable QUARANTINE CHANNEL.

21:00-26:00 - LEARNED COPY

The GHOST uses:
- correct voice
- correct frequency
- current authentication
- one copied speech habit

The player must use a contextual contradiction or information from the other agent.

Purpose:
Test the full verification system.

26:00-30:00 - FINAL CONTACT

At least one trusted information source becomes unreliable.

Possible conflicts:
- terminal versus paper
- map versus agent report
- quarantined route versus active carrier

The player makes one final operational decision.

The ending depends on:
- earlier trust decisions
- agent reachability
- channel quarantine state
- GHOST access

The final decision must use mechanics that the game taught earlier.


11. SCENARIO STATE

Use a small state model.

Track:
- ECHO-ACTUAL location
- ECHO-ACTUAL status
- ECHO-2 location
- ECHO-2 status
- available channels
- quarantined channels
- information that the GHOST has learned
- required scenario flags

Do not add simulation data that does not affect a later contact.


12. BRANCHING AND ENDINGS

Use a mostly shared scenario sequence.

Use conditional dialogue and state changes.

Do not create a large branching narrative tree.

Track only decisions that affect:
- future contact availability
- agent status
- channel availability
- GHOST access
- ending selection

Use three ending families.

CONTAINED
The operator keeps sufficient genuine communication and isolates the GHOST.

ISOLATED
The operator stops the GHOST but loses contact with one or both agents.

OPEN LINE
The operator leaves a critical route open or trusts the copied identity at a critical point.


13. ROOM AND VISUAL DIRECTION

Model one communications room in Blender.

Use:
- simple geometry
- basic materials
- limited color palette
- strong lighting
- few decorative assets

Generate CRT and terminal graphics in code.

The player remains seated or moves only within the workstation area.

The player must be able to look quickly between:
- radio
- spectrum display
- terminal
- paper reference
- field map
- microphone
- quarantine control

These objects form the physical gameplay loop.


14. PLAYER BODY AND INPUT

Use one rigged arm.

Animate only repeated gameplay actions:
- turn frequency dial
- adjust signal-quality control
- use authentication control
- use push-to-talk
- use quarantine control

Do not create unique hand animations for non-core props.

Controls:

MOUSE
Look.

LEFT MOUSE
Interact or drag.

MOUSE WHEEL
Fine-tune the radio.

KEYBOARD
Use terminal shortcuts when required.

PUSH-TO-TALK / CONFIRM
Send the selected response.


15. AUDIO

Audio is gameplay information.

Each agent needs:
- one stable voice identity
- consistent speech habits
- consistent radio processing

Use authored TTS lines if the result is clear and consistent.

Suggested processing:

VOICE
-> band limit
-> compression
-> light saturation
-> static/noise
-> signal-quality degradation
-> limited dropout

Do not remove required information with audio effects.

If an important word is not clear, REPEAT must remain available.

Use the copied agent voice for the GHOST.

Do not identify the GHOST with a special horror filter.


16. CONTENT LIMITS

Initial target:

ROOM
- 1 environment

CHARACTERS
- 2 agent voices
- 1 GHOST that uses copied voices

FIELD LOCATIONS
- 3-4

MAJOR CONTACTS
- approximately 8

AUTHENTICATION PAIRS
- 4-6

IMPORTANT PLAYER DECISIONS
- approximately 5

QUARANTINE DECISIONS
- 1-2

ENDING FAMILIES
- 3

CORE INTERACTIVE OBJECTS
- radio
- spectrum display
- terminal
- paper reference
- field map
- microphone
- quarantine control

If new content exceeds this limit, remove or replace existing content.


17. DEVELOPMENT PRIORITIES

P0 - 5-MINUTE PROTOTYPE

Build:
- room blockout
- radio tuning
- one signal-quality control
- spectrum display
- one ECHO-ACTUAL contact
- authentication paper
- HOLD / PROCEED
- one consequence contact

Success condition:
A player can complete TUNE -> VERIFY -> DECIDE after one guided contact.

P1 - 10-MINUTE HORROR SLICE

Add:
- ECHO-2
- first false contact
- contextual contradiction
- communication log
- duplicate voice

Success condition:
The player can identify the false contact from evidence.

P2 - COMPLETE SCENARIO

Add:
- all major contacts
- quarantine
- required scenario branches
- final contact
- three ending families

P3 - POLISH

Priorities:
- voice clarity
- radio feedback
- interaction speed
- screen readability
- lighting
- pacing
- restart flow
- build stability


18. CUT LIST

Do not add these systems to the initial version:
- third field agent
- multiple receiver banks
- full radio simulation
- patch-panel minigame
- router puzzle
- resource economy
- threat percentages
- procedural signal generation
- generic cipher puzzles
- complex tactical map
- free exploration
- inventory
- combat
- dynamic AI dialogue
- large narrative tree
- high scores


19. DESIGN RULES

- End each major contact with a decision or useful discovery.
- Keep tuning short.
- Make identity a result of evidence.
- Do not display a fake-caller probability.
- Treat authentication as proof of knowledge only.
- Let the GHOST learn a rule before it breaks the rule.
- Continue the scenario after most wrong decisions.
- Show consequences in later contacts.
- Provide a communication log for recent facts.
- Use only two agents in the initial version.
- Use one sacrifice mechanic.
- Reuse the same workstation.
- Use the first five minutes to teach mechanics used in the final contact.
- Remove a mechanic if it has no clear result within the 30-minute scenario.
